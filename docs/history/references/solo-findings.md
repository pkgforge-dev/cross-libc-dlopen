## What solo is

A **static-musl** process that loads **host glibc** libraries, using its own ELF
loader (`lib/elf_loader.cpp`, 2707 lines) and a hand-written glibc-to-musl ABI
bridge (`lib/glibc_shim.cpp`, 5948 lines). The host's own loader is never
consulted.

⚠ **Direction matters and is easy to get backwards.** solo goes
static-musl-process -> host-glibc-library. This project goes
bundled-glibc-process -> host-musl-or-newer-glibc-library. They are not the same
problem reversed: solo owns the whole process image and can therefore intercept
at the libc boundary, while this project is a guest inside somebody else's
process and intercepts only `dlopen`. ⭐ **That single difference explains
almost every divergence below**, including the one finding that matters most.

## Findings

### F1 -- solo FIXES both struct hazards this project calls unfixable -- **adopt**

⭐ **The most valuable thing in the sweep, and it corrects a claim here.**

[`docs/limits.md`](../../limits.md) says two glibc-vs-musl struct hazards
are live and "an offset compiled into an object is not reachable from a
preload". solo repairs both:

| hazard | solo, at file and line |
|---|---|
| `regmatch_t` stride | `lib/glibc_shim.cpp:3029` -- *"glibc regmatch_t holds int offsets while musl's are 64-bit"*. It declares its own `GlibcRegmatch` (`:3069`) and `sh_regexec` (`:3092`) calls the real `regexec` into a native `regmatch_t buffer[16]`, then translates on the way out |
| `FTW_*` off by one | `lib/glibc_shim.cpp:3456` -- *"musl's `FTW_*` type codes are glibc's plus one"*. `sh_nftw_trampoline` (`:3460`) passes `type - 1` to the guest's callback |

⛔ **This does NOT make the claim here wrong -- it makes it imprecise, and the
imprecision matters.** "Not reachable from a preload" is true of a preload that
interposes only `dlopen`. It is false of anything that interposes the *call*.
solo can do this because it supplies the whole libc; a `dlopen` interposer
could reach the same two by additionally interposing `regexec` and `nftw` and
translating at the boundary -- which is a narrow, testable piece of work, not an
architectural change.

The sentence to correct is the *reason*, not the measurement. E50's measurement
stands.

### F2 -- a machine-generated ABI difference table, kept honest by CI -- **adopt**

`dev/abi-diff.txt` (418 lines), generated by `dev/abi_diff.py` from
`dev/abi_probe.c`, and re-run in CI as the `abi_diff` step
(`.github/workflows/ci.yml`, `ubuntu-clang` job).

Its header line:

```
abi probe: 396 ok, 18 DIFF, 2 glibc-only, 0 musl-only
```

⭐ **416 probes.** This project's E50 measures a hand-picked six and reports two
live. solo probes the whole surface and prints every row, `ok` ones included, so
"we checked and it matched" is visible rather than absent.

⚠ **The two projects agree where they overlap**, which is a real independent
confirmation: `abi-diff.txt` lists `size regmatch_t 8 / 16`, `FTW_D 1 / 2`,
`size ucontext_t 968 / 936` and `value O_LARGEFILE 0 / 32768` -- the same four
this project names, with the same directions, and it further lists
`struct_rusage 144 / 272` and `struct_sched_param 4 / 48` as DIFF where this
project measured them as crossing harmlessly.

⛔ **That last pair is a genuine disagreement and it is not resolved here.** It
is very likely a difference of question -- solo probes `sizeof`, this project
probes whether the *fields it uses* sit at the same offsets -- but "likely" is
not a measurement. Written up as [`docs/todo/measurement.md`](../../todo/measurement.md) T-04.

### F3 -- the corpus test -- **adopt**

`tst/corpus.py` plus `tst/corpus_load.cpp`. Each corpus library is loaded
**eagerly, in a fresh process of its own**, with its declared dependency
packages extracted beside it; per-library results land in JSON, and the merged
report is emitted as an lcov trace mapped onto the lines of the platform's
glibc symbol inventory -- so the coverage service shows which ABI entries the
corpus demands and which of those only have stubs.

⭐ **"Which entries only have stubs" is the idea worth stealing.** This project
knows how many entry points resolved; it does not have a per-symbol view of
which ones are load-bearing versus decorative.

⚠ **Measured size, and it is not the number this repository has been
repeating.** `tst/corpus_x86_64.json` is a dict with two keys, `packages` and
`snapshot`; `packages` holds **1176** entries (aarch64: **1172**). Those are
*packages*, not objects -- the object count is not stated in the manifest and I
did not fetch the corpus to count them. See F6.

### F4 -- solo replaces the loader; this project deliberately does not -- **confirms**

`lib/elf_loader.cpp` implements symbol lookup with full version matching:
`findSymbol(name, version)` (`:310`), `matchSymbol` (`:311`), `parseVersions`
(`:305`), `searchScope` (`:403`), and its own `glibc-ld.so.cache` reader
(`:1401`).

This is the design [`docs/rejected-designs.md`](../../rejected-designs.md)
refuses, with a measurement. **Both positions are defensible and they are
answers to different questions**: solo owns the process, so replacing the loader
costs it nothing it was not already paying; this project is a preload inside a
loader it does not own, where replacing it means replacing the host's.

### F5 -- solo has no answer to gap 2, because it is not solo's problem -- **confirms**

`grep -riE 'glvnd|libGLX|GLESv2|egl_vendor'` over `lib/`, `bin/` and `tst/`
returns **nothing outside the corpus package lists** (`libglvnd0`,
`libglx-mesa0`, `libglx0` appear only as package names to be downloaded).

⭐ **The dispatcher-with-no-vendor failure is this project's distinctive
contribution**, and the sweep is evidence for that rather than against it. solo
does not hit it because a static-musl process bundling its own stack does not go
looking for a `libGLX_<vendor>.so.0` the host was supposed to ship.

### F6 -- the prior-art claim in this repository was written from reading -- **correct it**

[`docs/report/README.md`](../../report/README.md):2128 says solo has *"CI across Alpine,
Fedora, NixOS and Termux plus a 2100-object corpus test per commit."*

Checked against `.github/workflows/ci.yml` at the commit above:

| the claim | what the file says |
|---|---|
| CI across Alpine, Fedora, NixOS, Termux | **holds, and is understated.** Nine jobs: `alpine-musl`, `fedora-gcc`, `ubuntu-clang`, `ubuntu-arm`, `ubuntu-qemu` (boots a kernel under qemu), `nixos-lavapipe`, `termux-bionic-x86_64`, `termux-bionic-aarch64`, plus two corpus-fetch jobs. Both architectures. On every push **and** every pull request |
| a 2100-object corpus test | ⚠ **not what I can verify.** The manifest lists 1176 packages (x86_64). 2100 may well be the object count after unpacking; I did not fetch the corpus, so I cannot state it |
| -- | ⭐ **also present and unmentioned here:** `abi_diff`, `secure_test`, `rootfs_smoke`, `qemu_smoke`, `pthread_test`, `bionic_test`, `vulkan_test`, and Codecov coverage upload |

⛔ The number is corrected to what was measured, and the rest of the row is
widened, not narrowed. It is a genuine advantage for solo and the comparison
says so.

### F7 -- NixOS publishes ICD manifests outside the FHS -- **filed elsewhere**

Tracker, [issue #2](https://github.com/pg83/solo/issues/2): a NixOS user with a
GTX 1660 got `vkCreateInstance failed: VkResult -9` -- ⚠ **the same result code
this project's E31 predicts, from a different cause.** The maintainer fixed it
in `9e06d40`: the embedded Khronos loader now also scans
`/run/opengl-driver/share`, where NixOS publishes ICD manifests and which
nixpkgs patches into its own vulkan-loader.

solo's `nixos-lavapipe` CI job now reproduces that layout deliberately: it
symlinks the store's `share` to `/run/opengl-driver/share` and then **deletes**
`/usr/share/vulkan`, `/usr/local/share/vulkan` and `/etc/vulkan`, so no FHS path
can satisfy the test by accident.

⭐ **That last move is the technique worth having**: remove the path that would
mask the failure, so a pass means what it says. This project's host matrix has
no NixOS in it. Work: [`docs/todo/measurement.md`](../../todo/measurement.md) T-05.

### F8 -- solo's tracker is small and its PRs are substantive -- **no action**

Five items total. Two open (a `/proc/self/exe` PR, a build-permissions issue),
three closed -- two merged outside PRs about `RUNPATH` lookup from loaded code
and `--eh-frame-hdr` in static links, and the NixOS issue in F7. Nothing here
suggests a class of failure this project has not considered.

## Verdict

**adopt**, on four specific mechanisms (F1, F2, F3, and F7's masking-path
technique), each with a task. **confirms** on two design positions (F4, F5).
One claim in this repository is **corrected** (F6).

## ⛔ What this sweep did NOT do

- **Did not build or run solo.** Every claim above is read out of source, CI
  configuration and the tracker. No behaviour of solo was measured.
- **Did not fetch the corpus**, so the object count in F3/F6 stays unstated
  rather than estimated.
- **Did not read `lib/glibc_shim.cpp` in full.** 5948 lines; I read the regex,
  `nftw` and stub-fallback regions and skimmed the rest. A claim about what the
  bridge does *not* cover would need the full read and is not made.
- **Did not read `lib/elf_loader.cpp` in full** -- the version-matching and cache
  regions only.
- **Did not examine** `lib/bionic_shim.cpp`, `lib/musl_tls.c`, `bin/vulkan/`, or
  `ext/`.
- **Did not delegate any of the reading**, per the methodology.
